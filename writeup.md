# Week 4 Writeup — Link Shortener

**Agent:** Claude Code. **Feature:** click counter (`GET /stats/{code}`). **Result:** 10 tests pass (3 original, 7 new).

**1. `AGENTS.md`.** About 45 lines: what the service does, where `main.py`, `test_main.py` and `docs/TASKS.md` are, install/run/test commands, product boundaries (no auth, UI, other databases or dependencies), conventions, and the understand → test → implement → verify workflow. It is always loaded because every task needs it. The one non-obvious fact I included is that `CREATE TABLE IF NOT EXISTS` never alters an existing table; I found this by reading the real `links.db`, and it shaped the whole feature.

**2. Scoped instruction.** `.claude/rules/testing.md` carries a `paths:` filter for `test_*.py`, `**/test_*.py` and `conftest.py`. It loads only when test files are involved. Its rules: test through the public API, cover success and failure, never assert on specific generated codes because tests share one `links.db`, and use `follow_redirects=False` for redirects. It stays out of the way for unrelated work such as routing or schema changes, so it costs no context there. The starter keeps tests in a root file, so a path glob fit better than a `tests/AGENTS.md`.

**3. Reusable workflow.** `.claude/skills/add-feature/SKILL.md` encodes seven steps: read the task and guidance, inspect code and tests, state behavior and risks before editing, write a failing test, make the smallest change, run `pytest`, summarize with remaining risks.

**4. Discovery (tool mapping).** `CLAUDE.md` contains only `@AGENTS.md`, because Claude Code reads `CLAUDE.md` and this keeps one shared source. Rules in `.claude/rules/` load by their `paths:` match, and skills in `.claude/skills/` are discovered by their `description` and invoked by name. Honest limits: I created these files mid-session, so I did not see the rule auto-load or invoke the skill through the tool; I followed the skill's steps by hand. Plan and review were separate read-only passes by the same agent in the same session, not an independent reviewer.

**5. What planning and review caught.** Planning found that the existing database has no `clicks` column; without an `ALTER TABLE` migration the feature would pass fresh-database tests and crash on a real one. I added `test_old_database_without_clicks_column_is_upgraded`. It also decided to count only successful redirects, with one atomic `UPDATE ... clicks = clicks + 1`. Review returned **REVISE**: one test name claimed more than it proved, and my test rule contradicted the migration test. I fixed both. I also stress-tested the "no lost counts" comment: 100 requests across 20 threads produced exactly 100 clicks. A security scan flagged sequential, guessable codes (`encode(row_id)`); that is the starter's design, outside this task, so I only noted it.

**6. Lessons.** Short, always-on context plus narrowly scoped rules beats one long file. The most valuable guidance was a fact the agent could not infer from code alone. Planning without editing is cheap and found the real risk. And a passing test suite only proves what the tests check, so I verified the concurrency and migration claims separately.
